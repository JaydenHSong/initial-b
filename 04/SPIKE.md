# S04 스파이크 기록

## 1. 아마존 재판정 — **됐다 (오늘은 직접이 뚫린다)** (2026-08-25)

**판정 질문:** S02에서 8/10에 막혔던 아마존 직접 fetch가 오늘 `initial-b04`(iad1)에서 뚫리나?

**방법:** S02 `cron.js`의 direct/readPrice를 `04/api/spike-fetch.js`로 옮겨 배포, 3회 호출. 버릴 코드.

| 회차 | status | bytes | ms | price |
|---|---|---|---|---|
| 1 | 200 | 1002KB | 1484 | **139.98** |
| 2 | 200 | 997KB | 1753 | **139.98** |
| 3 | 200 | 999KB | 1405 | **139.98** |

- 3/3 성공, 봇 페이지·소프트 차단 마커 0건. S02 수치(1.44초/건)와 거의 같다.
- **S02 교훈 그대로: "오늘 열림 ≠ 계속 열림"** (8/7 4/4 → 8/10 0/5 전례). 그래서 구현은
  처음부터 직접 → 실패 건만 프록시 폴백 구조로 간다.
- **프록시 폴백은 미판정.** `BRD_WS`가 initial-b04에 없고, 오늘은 직접이 뚫려 폴백 경로를
  탈 수도 없다. 코드는 배포돼 있으니(spike-fetch가 직접 실패 시 자동 폴백) **차단이
  돌아온 날 그대로 재판정하면 된다.** → 수요일 전에 `BRD_WS`를 **Bright Data 대시보드
  원본에서** initial-b04에 등록해둘 것 (`vercel env pull` 복사는 `[SENSITIVE]` 가짜 값 —
  S03 실측). 등록 후 재배포 필수.

**배관 재판정 (같은 날 오후, BRD_WS 등록 후) — 407로 미해결.** 없는 ASIN으로 폴백을
강제하니 Bright Data 접속이 74ms 만에 `407 Proxy Authentication Required`. 재등록
후에도 동일. 값의 **모양**은 정상이다(`?probe=1`로 스킴·인증부·호스트만 관측 —
비밀은 안 찍는다): `wss://brd-customer-***-zone-scraping_browser2:(10자)@brd.superproxy.io:9222`.
형식이 맞는데 407이면 **존 비활성 또는 비밀번호 불일치**다. 2회 시도 후 3번 규칙 전에
멈추고 구현을 먼저 했다 — 직접 경로가 뚫리는 오늘은 폴백이 이번 주를 막지 않는다.
재판정 방법: 대시보드에서 존 상태/비번 확인 후 재배포 → 없는 ASIN 드랍 → note에
프록시 관측이 남는지.

**셋업 시간:** 약 3분 (04/ 생성 → `vercel project add initial-b04` → 배포 → 첫 판정.
S02 코드와 검증된 의존성 버전을 그대로 옮긴 덕)

**문서 품질:** 해당 없음 (공식 API 아님, S02 재료 재사용)

**무료 한도:** 직접 fetch 비용 0 (~1MB/건). Vercel Hobby 함수 한도에 여유.

## 2. "즉시 응답 + 백그라운드 채움" — **됐다 (단, waitUntil로만)** (2026-08-25)

**판정 질문:** 등록 함수가 즉시 응답한 뒤, 기다리지 않고 트리거한 수집 함수가
죽지 않고 끝까지 도나? — 이번 주 진짜 판정.

**방법:** `spike-bg`(트리거, 두 모드) + `spike-slow`(5초 자고 아마존 1회 긁고 로그 마커).
완주 여부는 런타임 로그의 `SPIKE_SLOW_DONE`으로 판정.

| 모드 | 트리거 응답 | 잡 완주 | 관측 |
|---|---|---|---|
| `ff` — fetch를 안 기다림 | 0.245s | **가짜 성공 → 단독 재판정에서 실패** | 아래 |
| `wu` — `waitUntil(fetch)` | 0.178s | **완주** — 트리거 0.1초 뒤 시작, 6.5초 뒤 DONE + 가격 추출 | PASS |

**막힌 지점 1개 — fire-and-forget이 "된 것처럼 보였다."** 첫 실측에서는 ff 잡도
완주했다. 그런데 타임스탬프가 이상했다: ff 트리거는 12:32:47.5인데 잡 시작이
12:32:49.85 — **2초 뒤 wu 요청이 들어온 바로 그 시각**이다. 응답을 보내는 순간
안 기다린 fetch는 인스턴스와 함께 얼려지고, 다음 요청이 인스턴스를 깨울 때
해동돼 나간 것. ff만 단독으로 다시 쏘고 후속 트래픽 없이 40초를 기다리니
**실행 0회** — START 로그조차 없다. 트래픽이 있는 데모에서는 우연히 돌고,
없는 새벽에는 조용히 안 도는 최악의 형태다. S02 "관측값이 우연에 오염된다"
계열의 함정. **구현은 무조건 `waitUntil`(@vercel/functions)로.**

**곁가지 함정:** `vercel logs`는 테일이 아니라 **1회성 조회**다 (긁고 바로 종료).
트리거 전에 걸어두면 빈손이 된다 — 판정 후에 조회해야 한다.

**구현 힌트 (수요일):** 함수를 둘로 나눌 필요도 없을 수 있다 — 등록 함수 하나가
행을 쓰고 즉시 응답한 뒤 `waitUntil(collect())`로 수집까지 품는 모양이 최단.
`maxDuration`은 프록시 폴백(9~47초) 감안해 60으로.

**셋업 시간:** 판정 1과 같은 배포에 포함 (추가 0분)

**문서 품질:** 기록 없음 (import 한 줄에 첫 시도 성공이라 문서를 볼 일이 없었다)

**무료 한도:** waitUntil로 잡히는 시간도 함수 실행 시간에 포함 — Hobby 한도에서
등록당 수십 초 × 팀 규모 수준은 문제없다.
