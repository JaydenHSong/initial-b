01누가 쓰나

경쟁 제품의 아마존 가격을 챙겨야 하는 이커머스 운영 담당자. 아침마다 경쟁 ASIN을 탭으로 하나씩 열어 확인한다.

02지금은

상품 페이지를 브라우저로 열고 가격을 눈으로 읽어 옮겨 적는다. 제품 수 × 탭 하나씩. 긁는 도구를 만들려던 S03 시도는 "요청 안에서 기다리는 동기 수집은 성립 안 한다"(9~47초 지연, 타임아웃 40%)로 판정 났다.

03없앨 동작 하나

수집이 끝날 때까지 화면 앞에서 기다리는 것. 등록과 수집을 분리해 40초 지연을 UX가 아니라 파이프라인으로 만든다.

04핵심 기능 1개

아마존 상품 URL을 드랍하면 카드가 즉시 「수집 중」으로 등록되고, 백그라운드 수집이 가격·제목·메인 이미지·별점을 채우면 카드가 저절로 갱신된다. 상태는 수집 중 / 성공(가격+시각) / 차단됨 / 실패 네 가지. 다시 긁기 = 같은 URL 재드랍.

05안 만드는 것 3개

  • 정기 크론 수집·가격 히스토리 — S02에서 이미 증명했다(크론은 S09 카드). 등록 시점 1회 수집만
  • 목표가 알림 — S02에서 했고 S12 카드다
  • 아마존 외 사이트 파서 — ASIN 파서 1개. 경쟁사 제품도 아마존 페이지로만 긁는다

06성공 판정

  • URL 드랍 → 1초 안에 「수집 중」 카드가 뜬다 (등록 함수는 기다리지 않는다)
  • 수십 초 안에 가격·제목이 저절로 채워진다 (새로고침 없이 폴링)
  • 없는 상품·차단은 관측값(바이트 수·마커)과 함께 상태로 갈려 남는다 — 틀린 값을 저장하지 않는다

07내 옵션 + 이유

수집기 자체는 S02에서 검증된 재료다(직접 fetch가 막히면 Bright Data 폴백, 4/5·건당 ~11초). 이번 주의 새 부분은 비동기 연결부 하나 — 등록 함수가 행만 쓰고 즉시 응답한 뒤 waitUntil()로 수집을 품는다. 저장을 Supabase로 한 것은 01 갤러리의 드랍 뼈대(URL upsert·merge-duplicates)를 코드째 재활용할 수 있고 S05 Postgres 통합주 예습을 겸해서다.

08리스크 + 검증법

걱정되는 것: ① 아마존 차단 재발 — 오늘 열려 있어도 내일 막힐 수 있다(S02: 8/7 4/4 → 8/10 0/5) ② 응답 후 백그라운드 작업이 서버리스에서 실제로 도는가
화요일 스파이크로 확인: ① 직접 fetch 3/3 성공(1.5초, 가격 추출) — 폴백 배관은 BRD 407로 미판정, 코드는 준비됨 ② fire-and-forget은 가짜 성공(인스턴스와 함께 동결), waitUntil은 완주 — 상세 04/SPIKE.md
