# S02 스파이크 기록

## 1. 아마존 가격 수집 — **됐다** (2026-08-07)

**판정 질문:** Vercel 서버리스(데이터센터 IP)에서 아마존 상품 페이지를 받아 가격이 나오나?

**방법:** `02/api/price.js` 10줄 배포 → `GET /api/price?asin=B0H1GTPMC4` 호출.
버릴 코드다. UI·예외처리 없음.

**결과: 4회 연속 성공**

| 회차 | status | price | blocked | ms |
|---|---|---|---|---|
| 1 | 200 | 76.98 | false | 1506 |
| 2 | 200 | 76.98 | false | 1483 |
| 3 | 200 | 76.98 | false | 1437 |
| 4 | 200 | 76.98 | false | 1360 |

- 응답 크기 약 1.0MB, 평균 1.44초
- CAPTCHA·봇 차단 흔적 0건 (`api-services-support`, `Enter the characters you see` 미검출)
- 가격은 HTML 안에 JSON으로 박혀 있다 → `/"priceAmount":([0-9.]+)/` 정규식 하나로 추출
- 제목도 같은 응답에서 나온다 → 등록 시 제목 자동 채우기가 공짜로 딸려온다
- 정가(`a-offscreen">$139.98`)도 같이 잡혀 할인율 계산 가능

**셋업 시간:** 약 20분 (Vercel 프로젝트 생성 → 함수 배포 → 첫 성공 응답)

**막힌 지점 1개:** 아마존은 `Accept-Encoding`을 보내지 않아도 **gzip으로 응답한다.**
로컬 첫 시도에서 HTTP 200에 203KB를 받고도 제목·가격이 전부 안 잡혔다. 압축을 안 풀고
문자열을 찾으면 조용히 빈손이 된다 — 에러가 안 나서 원인을 찾는 데 시간이 걸렸다.
서버리스에서는 `fetch()`가 자동으로 풀어주므로 재현되지 않았다.

**문서 품질:** 해당 없음 (공식 API가 아니라 HTML 파싱)

**무료 한도:** 비용 0. 다만 아마존 ToS 위반 소지가 있고, 차단은 IP 평판 기준이라
언제든 막힐 수 있다 → 크론이 조용히 죽지 않도록 실패 시에도 알림을 보낸다.

**파생 제약 (기획에 반영):**
- 검증은 Vercel 기본 리전 `iad1`에서 통과. **리전을 옮기면 나가는 IP가 바뀌어 재검증이
  필요하다** → `vercel.json`에 `regions`를 넣지 않는다.
- ~~1.44초 × 제품 수인데 함수 상한이 10초라 `Promise.all` 병렬 필수~~ → **뒤집혔다.**
  아래 4번 참고. 병렬이 오히려 차단을 불렀고, 상한은 `maxDuration`으로 늘리면 됐다.

## 4. 사흘 뒤 아마존이 막았다 (2026-08-10)

**8/7에는 4회 연속 성공, 평균 1.44초.** 8/10 첫 자동 크론에서 5건 중 4건 실패 알림이 왔다.
"조용히 죽지 않는다"고 넣어둔 실패 알림이 실제로 값을 한 첫 사례다.

**진단 과정에서 두 번 틀렸다.**

처음엔 제품 문제인 줄 알았다. 그런데 08:00 크론에서는 `B0H1GTPMC4`만 통과했는데 수동으로
다시 돌리니 `B09B8V1LZ3`만 통과했다 — **매번 1개, 통과 대상이 바뀐다.** 동시 요청
스로틀링으로 보고 `Promise.all` 을 직렬 + 0.7~1.6초 간격으로 바꿨다. 차단은 그대로였다.

그다음엔 전부 차단인 줄 알았다. 실패 사유에 받은 바이트 수와 가격 마크업 개수를 실어
보내고 나서야 갈렸다:

| 사유 | 건수 | 근거 |
|---|---|---|
| 아마존 차단 (하드) | 3 | 3,781B 봇 확인 페이지. 직렬·3회 재시도에도 안 뚫림 |
| ~~판매자 없음(품절)~~ → **소프트 차단** | 2 | 1.2~1.4MB 정상 페이지 · `corePrice` 마크업 70개 이상 생존 · `Currently unavailable` |

**세 번째로 틀린 지점이 여기다.** `"priceAmount"` 가 구매 가능한 오퍼가 있을 때만 생기는
필드인 건 맞다. 그래서 이 2건을 진짜 품절로 판정했는데 — **프록시를 붙여보니 같은 ASIN이
$31.99, $19.99 로 멀쩡히 나왔다.** IP만 바꿨을 뿐인데 값이 나온다.

즉 아마존은 의심 IP에 봇 페이지만 주는 게 아니라, **정상처럼 보이는 페이지에서 가격만 빼고
「Currently unavailable」을 대신 넣기도 한다.** 이 소프트 차단은 진짜 품절과 페이지상 구분이
안 된다 — **관측만으로는 못 가르고, 다른 경로로 같은 걸 받아봐야 안다.**

**막힌 지점 1개:** 실패 사유를 「품절이거나 차단」으로 뭉뚱그려 놓은 것. 대응이 완전히
갈리는 두 경우를 한 문장에 묶어둬서, 원인을 가르는 데 배포를 여러 번 돌렸다. **에러
메시지에 판단을 미리 섞지 말고 관측값(바이트 수·마커 유무)을 남겨야 한다.** 그리고 그
관측값조차 상대가 속이면 틀린다는 것을 이번에 배웠다.

**안 한 것:** `a-offscreen` 값으로 폴백하려다 접었다. 골프장갑 페이지에서 뽑은 값이
골프공 가격($31.99)이었다 — 연관상품 가격이 섞여 **틀린 값이 조용히 저장될 뻔했다.**
값이 없는 것보다 틀린 값이 나쁘다.

**대응 (8/10 오후):** Bright Data 스크래핑 브라우저를 **폴백으로만** 붙였다. 직접 fetch 를
먼저 하고, 가격을 못 얻은 건만 프록시로 다시 받는다. 전부 프록시로 돌리지 않는 이유는
비용도 있지만 **직접 성공률이 계속 기록돼야 차단 추세가 보이기 때문**이다. 아마존이 다시
풀어주면 자동으로 무료 경로로 돌아온다.

| | 8/7 | 8/10 직접만 | 8/10 프록시 폴백 |
|---|---|---|---|
| 성공 | **4/4** | **0/5** | **4/5** |
| 건당 | 1.44초 | — | 약 11초 |
| 비용 | 0 | 0 | 약 4센트/일 ($8/GB, 건당 ~1.1MB) |

프록시 쪽에서 막힌 지점도 하나 있었다. 트래픽을 아끼려고 이미지·폰트에 **CSS까지** 막았더니
아마존 JS 렌더 타이밍이 틀어져 291KB짜리 반쪽 HTML을 읽거나 45초 타임아웃이 났다. CSS는
다시 받고, 가격이나 품절 표시가 나올 때까지 최대 12초 기다렸다 읽는 것으로 정리했다.

## 2. Firestore 다대다 태그 — **됐다 (우회해서)** (2026-08-07)

**판정 질문:** 문서형에서 태그 N개 AND 질의가 되나?

**환경:** 프로젝트 `initial-b`(개인 계정) · `(default)` · **`us-west1`** · Native 모드.
제품 5개 + 각 3일치 가격을 심고 쟀다.

| 확인한 것 | 결과 |
|---|---|
| `array-contains` 두 번 | **안 된다** — `A maximum of 1 'ARRAY_CONTAINS' filter is allowed per disjunction.` |
| `array-contains-all` | **그런 연산자가 없다.** SDK가 거부하며 허용 목록을 뱉는다 (`<, <=, ==, !=, >, >=, array-contains, in, not-in`) |
| `array-contains-any` | 되지만 **OR다.** "보안카메라 또는 무선" = 4개, AND 정답 2개와 다르다 |
| 우회 — 서버 1개 + 클라이언트 필터 | **된다.** 서버가 3개 돌려주고 그중 2개가 정답 (64ms) |
| 태그 필터 + `lastPrice` 정렬 | **복합 인덱스 필요.** 에러에 인덱스 생성 링크가 딸려온다 |

**핵심:** 태그가 늘수록 서버는 첫 태그 하나로만 좁히고 나머지는 클라이언트가 버린다.
이번 실측에서 3개 읽어 1개를 버렸고, **버린 문서도 읽기 요금에 포함된다.** 태그가 흔할수록
버리는 비율이 커진다. 관계형이면 조인 테이블에 `GROUP BY product_id HAVING COUNT(*) = N`
한 방이고 버리는 문서가 없다.

**쓰기 성능:** 제품 5개 + 가격 15개 = 20회 쓰기에 2,307ms (직렬). 등록은 건당 1회 쓰기라
여유가 크다.

**곁가지로 잰 것 — S09에 넘긴다 (이번 주 범위 아님)**

가격을 매일 쌓는 방향을 잠깐 검토했다가 접었다(크론은 S09, 알림은 S12 스택 카드다).
접기 전에 서브컬렉션 비용을 재놨으니 그때 쓰라고 남긴다.

| 방식 | 읽기 | 시간 |
|---|---|---|
| `prices` 서브컬렉션 전부 읽어 최저가 계산 | **20회** | 403ms |
| 제품 문서에 `minPrice`를 중복 보관하고 그것만 읽기 | **5회** | 44ms |

제품 N개·기록 M일이면 `N*(M+1)` 대 `N`이다. 하루 1회로 18주면 제품당 126일치가 쌓이므로,
시계열을 붙이는 순간 비정규화가 사실상 강제된다. 대가는 쓰는 쪽이 두 곳을 맞춰야 하는
정합성 부담이다.

**막힌 지점 1개:** `firebase-admin` 최신 버전은 루트 CJS 익스포트가 바뀌어
`require('firebase-admin').credential`이 `undefined`다. 모듈러 진입점
(`require('firebase-admin/app')`의 `initializeApp`·`cert`)을 써야 한다. 예전 예제를
그대로 쓰면 `Cannot read properties of undefined (reading 'cert')`로 죽는다.

**문서 품질:** 중 — 연산자 목록과 인덱스 에러 링크는 친절한데, `array-contains-all`이
없다는 사실은 문서에서 바로 안 보이고 직접 부딪혀야 알게 된다.

**무료 한도(Spark):** 일 읽기 50,000 · 일 쓰기 20,000 · 저장 1GiB. 제품 20개를 하루 1회
수집해도 쓰기 40회/일이라 여유가 크다.

**부수 확인:**
- 조직 정책 `iam.disableServiceAccountKeyCreation`은 회사 조직에서 미적용이었으나, 훈련용이라
  **개인 계정 프로젝트로 갔다.** 회사 조직(`1006423402956`)의 빈 `initial-b02`는 안 쓴다.
- 로컬 gcloud가 Python 3.9라 `gcloud firestore databases create`가 크래시한다
  (`CommandLoadFailure`). 데이터베이스 생성은 콘솔에서 했다.

**정리 완료 (8/7):** 스파이크가 심은 `products` 5개와 하위 `prices` 15개를 전부 지웠다.
`B0H1GTPMC4`는 ASIN만 진짜고 태그·가격은 지어낸 값이라 같이 지웠다 — 반쯤 가짜인 데이터가
남아 있으면 「데이터 하드코딩 금지」 판정에서 헷갈린다. **저장소는 지금 비어 있고, 데모용
데이터는 실제 등록 흐름으로 넣는다.**

**남은 확인:** 브라우저에서 보안 규칙으로 읽히는지(읽기 공개·쓰기 금지)는 구현 때 같이 본다.
→ 확인됨: 읽기 200, 브라우저에서 쓰기 시도 403. `prices` 서브컬렉션까지 읽히려면 규칙에
`match /products/{asin}/{sub=**}` 를 따로 열어야 한다. 상위 문서 규칙은 하위를 안 덮는다.

## 3. 크론 + 알림 — **됐다** (2026-08-08, 범위 확대분)

크론(S09)과 알림(S12)을 이번 주로 당겨 쓰기로 하면서 추가로 얻은 것들.

**Vercel Hobby 크론은 하루 1회가 상한이다.** 마침 요구사항이 하루 1회라 걸리지 않았지만,
더 자주 돌려야 했으면 여기서 막혔다. `vercel.json` 의 `crons` 는 프로덕션 배포에만 등록된다.

**함수 상한 10초 × 제품당 1.44초 = 6개에서 죽는다.** 크론은 `Promise.all` 로 병렬화했다.
직렬로 짰다면 제품이 늘어난 어느 날 조용히 타임아웃 났을 것이다.

**막힌 지점 1개 — 환경변수는 배포 시점에 주입된다.** `CRON_SECRET` 을 등록하고 확인했더니
키 없이도 200이 나왔다. 원인은 프로덕션이 **변수 등록 이전 배포**에 머물러 있던 것.
게다가 재배포하려고 빈 커밋을 밀었는데 **Skip deployments 토글이 정상 동작해서** 건너뛰었다
(`Canceled`, 942ms) — 주차 폴더에 변경이 없으니 맞는 판단이다. 결국 `vercel redeploy` 로
직접 걸어야 했다. **앞으로 환경변수를 바꾸면 빈 커밋이 아니라 `vercel redeploy` 를 쓴다.**

**중복 알림 방지는 `hitAt` 한 필드로 됐다.** 목표가를 뚫은 시각을 문서에 적어두고, 있으면
다시 알리지 않는다. 가격이 목표 위로 돌아가면 그 필드를 지워 다음 하락에 다시 알린다.
실측으로 두 번째 크론 호출에서 `hits: 0, notified: null` 이 나오는 것을 확인했다.

**아무도 안 뚫렸는데 수집이 실패하면 그 사실을 알린다.** 며칠째 못 긁고 있는 걸 모르는 게
목표가를 놓치는 것보다 나쁘다고 보고 넣었다.
