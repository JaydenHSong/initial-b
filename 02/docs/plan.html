나 혼자. 아마존에서 경쟁 제품을 보다가 "이거 세일하면 사야지" 하고 탭을 열어두는 사람. 하루에 몇 개씩 쌓인다.

02지금은

탭을 열어두거나 링크를 나한테 슬랙 DM으로 보낸다. 가격이 떨어졌는지는 다시 들어가 봐야 알고, 대개 안 들어간다. 결국 탭을 닫으면 그걸로 끝이다.

03없앨 동작 하나

가격이 떨어졌나 보려고 다시 들어가는 것. 사람이 확인하러 가지 않는다 — 떨어졌을 때 쪽에서 먼저 온다.

04핵심 기능 1개

ASIN을 등록하면 하루 한 번 가격을 자동으로 쌓고, 지금까지의 최저가보다 낮아지면 Google Chat으로 알린다. 저장된 제품은 태그 여러 개로 묶이고, 태그를 여러 개 골라 전부 달린 것만 볼 수 있다(다대다 AND 필터).

등록 → 크론이 매일 수집 → 최저가 갱신 시 알림. 사람 손이 닿는 곳은 등록과 태그뿐이다.

05안 만드는 것 3개

  • 가격 차트·그래프 — 시계열을 쌓으면 제일 당기는 유혹이다. 숫자 목록으로 충분하고, 차트는 이번 주 스택 카드와 무관하다
  • 수정·삭제 UI — 잘못 넣으면 Firestore 콘솔에서 지운다. 로그인 없는 사이트에 삭제 버튼을 두지 않는다
  • 텍스트 검색·정렬 — 검색을 붙이는 순간 태그가 필요 없어지고 이번 주 주제가 사라진다

06성공 판정

  • ASIN 5개를 등록하면 제목·현재가가 자동으로 채워진다
  • 각 제품에 태그를 2개 이상 달고, 태그 칩 2개를 동시에 고르면 둘 다 달린 것만 남는다
  • 크론을 수동 트리거하면 그날 가격이 시계열에 쌓인다 (자동 실행 로그로 확인)
  • 최저가가 깨지면 Google Chat에 알림이 뜬다 — 데모에서 프로젝터로 보여준다
  • 수집이 실패해도 조용히 죽지 않는다 (실패도 알림 + 마지막 확인 시각을 화면에 표시)
  • 새로고침·다른 기기에서 같은 목록이 보인다 (하드코딩 아님)
  • 서비스 계정 키가 브라우저에 노출되지 않는다
  • 다대다 태그와 가격 시계열을 한 문서형 저장소에 어떻게 넣었는지 스키마로 설명한다

07내 옵션 + 이유

Firestore (문서형). 이번 주 주제가 "관계형과 문서형의 체감 차이"인데 S01에서 Supabase(관계형)를 이미 썼으니, 반대쪽을 잡아야 대비가 생긴다. 크론이 서버에서 도는 이상 localStorage는 구조적으로 탈락했고, Airtable은 무료 1,000레코드 한도라 매일 쌓이는 시계열에 안 맞는다.

결정적인 건 이번 주 데이터가 문서형의 고전 문제를 정확히 때린다는 점이다. 한 저장소에 성격이 다른 두 관계가 들어온다 — 다대다(제품 ↔ 태그)와 일대다 시계열(제품 → 매일의 가격). 문서 products/{asin}에 tagNames 배열을 두고 가격은 prices/{날짜} 서브컬렉션으로 뺐다.

그러면 목록 한 번 그릴 때마다 제품 수만큼 서브컬렉션 읽기가 터진다. 그래서 lastPrice·minPrice를 제품 문서에 중복으로 들고 다닌다. 대가는 크론이 매일 두 곳을 맞춰 써야 하는 정합성 부담이다. 관계형이면 MIN(price) 한 방이고 중복이 없다 — "왜 중복을 감수했나"가 이번 주에 배운 것이다.

쓰기는 크론(서버, Admin SDK), 읽기는 브라우저(클라이언트 SDK + 보안 규칙 읽기전용)로 갈린다. 리전은 us-west1 — 브라우저에서 직접 읽으므로 첫 로딩 초에 영향이 있다.

08리스크 + 검증법

걱정 1 — 아마존이 서버에서 긁는 걸 막는다: 차단 기준이 빈도가 아니라 IP 평판이라, Vercel의 데이터센터 IP가 걸리면 구조가 통째로 무너진다.
→ 확인 완료 (8/7): 됐다. 10줄짜리 함수를 배포해 4회 연속 200·가격 추출 성공, 평균 1.44초, 봇 차단 흔적 0건. 유료 API 없이 간다. 다만 언제든 막힐 수 있으므로 실패해도 조용히 죽지 않게 실패 알림을 넣는다. 파생 제약 둘 — 1.44초 × 제품 수인데 함수 상한이 10초라 크론은 병렬 필수, 그리고 검증이 iad1에서 난 것이라 리전을 옮기면 재검증해야 한다.

걱정 2 — 문서형에서 태그 N개 AND 질의: Firestore에는 array-contains-all이 없다. 태그 하나만 서버 질의로 걸고 나머지는 클라이언트에서 걸러내야 할 수 있다.
→ 확인 완료 (8/7): 우회해서 된다. 제품 5개를 심고 재보니 array-contains는 질의당 하나만 허용되고(A maximum of 1 'ARRAY_CONTAINS' filter is allowed per disjunction), array-contains-all은 연산자 자체가 없다. array-contains-any는 OR라 답이 다르다. 그래서 태그 하나만 서버에서 걸고 나머지는 클라이언트에서 버린다 — 실측에서 서버가 3개를 돌려주고 2개만 정답이었다. 버린 문서도 읽기 요금에 포함된다.
비정규화 효과도 쟀다: 최저가를 서브컬렉션 전부 읽어 계산하면 20회·403ms, 제품 문서의 minPrice만 읽으면 5회·44ms. 제품 N개·M일이면 N*(M+1) 대 N이다. 태그 필터에 가격 정렬을 붙이면 복합 인덱스가 따로 필요하다.
