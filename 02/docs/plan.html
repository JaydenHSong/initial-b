02지금은

탭을 열어두거나 링크를 나한테 슬랙 DM으로 보낸다. 나중에 "그거 뭐였지" 하고 DM을 거슬러 올라가지만 어떤 맥락으로 담아둔 건지는 안 남아 있다. 결국 탭을 닫으면 그걸로 끝이다.

03없앨 동작 하나

담아둔 제품을 다시 찾아 헤매는 것. 탭·DM을 뒤지는 대신 태그로 좁혀서 꺼낸다.

04핵심 기능 1개

ASIN을 등록하면 제목·가격을 한 번 채워 저장하고, 태그 여러 개로 묶어 태그를 여러 개 골라 전부 달린 것만 본다(다대다 AND 필터).

등록 → 저장 → 태그로 좁히기. 가격은 등록 시점의 값 하나만 남긴다 — 이번 주에 볼 것은 가격의 변화가 아니라 문서형 저장소가 다대다를 어떻게 감당하는가이다.

05안 만드는 것 3개

  • 가격 자동 추적 · 알림 — 매일 수집하는 크론은 S09, 알림 채널은 S12의 스택 카드다. 여기서 당겨 쓰면 그 주에 배울 게 없어지고, 이번 주 하루치 구현 시간이 태그 스키마가 아니라 크론 디버깅에 간다. 등록 시점 1회 수집이면 태그를 붙일 데이터로 충분하다
  • 수정·삭제 UI — 잘못 넣으면 Firestore 콘솔에서 지운다. 로그인 없는 사이트에 삭제 버튼을 두지 않는다
  • 텍스트 검색·정렬 — 검색을 붙이는 순간 태그가 필요 없어지고 이번 주 주제가 사라진다

06성공 판정

  • ASIN 3개 이상을 등록하면 제목·가격이 자동으로 채워진다
  • 각 제품에 태그를 2개 이상 달고, 태그 칩 2개를 동시에 고르면 둘 다 달린 것만 남는다
  • 수집이 실패해도 조용히 죽지 않는다 (실패를 화면에 남기고 제목 없이라도 저장된다)
  • 새로고침·다른 기기에서 같은 목록이 보인다 (하드코딩 아님)
  • 서비스 계정 키가 브라우저에 노출되지 않는다
  • 다대다 태그를 문서형 저장소에 어떻게 넣었는지 스키마로 설명한다

07내 옵션 + 이유

Firestore (문서형). 이번 주 주제가 "관계형과 문서형의 체감 차이"인데 S01에서 Supabase(관계형)를 이미 썼으니, 반대쪽을 잡아야 대비가 생긴다. localStorage는 "다른 기기에서 같은 목록"이 안 되므로 탈락했고, Airtable은 스프레드시트를 DB처럼 쓰는 것이라 다대다가 결국 쉼표 문자열로 뭉개진다.

결정적인 건 이번 주 데이터가 문서형의 고전 문제를 정확히 때린다는 점이다. 다대다(제품 ↔ 태그)는 관계형이면 조인 테이블 하나로 끝나는데, 문서형에는 조인이 없다. 문서 products/{asin}에 tagNames 배열을 얹는 것이 정석인데 — 그 배열로 AND 질의가 안 된다.

그래서 태그 하나만 서버에서 걸고 나머지는 브라우저에서 버린다. 관계형이면 WHERE tag IN (…) GROUP BY … HAVING COUNT(*)=2 한 방이고 버리는 행이 없다. 문서형은 정답이 아닌 문서까지 읽고 그 읽기에 요금이 붙는다 — "조인이 없으면 무엇을 대신 치르는가"가 이번 주에 배울 것이다.

쓰기는 서버 함수(Admin SDK), 읽기는 브라우저(클라이언트 SDK + 보안 규칙 읽기전용)로 갈린다. 리전은 us-west1 — 브라우저에서 직접 읽으므로 첫 로딩 초에 영향이 있다.

08리스크 + 검증법

걱정 1 — 아마존이 서버에서 긁는 걸 막는다: 차단 기준이 빈도가 아니라 IP 평판이라, Vercel의 데이터센터 IP가 걸리면 구조가 통째로 무너진다.
→ 확인 완료 (8/7): 됐다. 10줄짜리 함수를 배포해 4회 연속 200·가격 추출 성공, 평균 1.44초, 봇 차단 흔적 0건. 유료 API 없이 간다. 다만 언제든 막힐 수 있으므로 실패해도 조용히 죽지 않게 실패를 화면에 남기고 제목 없이라도 저장한다. 파생 제약 둘 — 등록 1건당 1.44초를 사용자가 그대로 기다리고, 검증이 iad1에서 난 것이라 리전을 옮기면 재검증해야 한다.

걱정 2 — 문서형에서 태그 N개 AND 질의: Firestore에는 array-contains-all이 없다. 태그 하나만 서버 질의로 걸고 나머지는 클라이언트에서 걸러내야 할 수 있다.
→ 확인 완료 (8/7): 우회해서 된다. 제품 5개를 심고 재보니 array-contains는 질의당 하나만 허용되고(A maximum of 1 'ARRAY_CONTAINS' filter is allowed per disjunction), array-contains-all은 연산자 자체가 없다. array-contains-any는 OR라 답이 다르다. 그래서 태그 하나만 서버에서 걸고 나머지는 클라이언트에서 버린다 — 실측에서 서버가 3개를 돌려주고 2개만 정답이었다. 버린 문서도 읽기 요금에 포함된다.
이게 이번 주 비교표에 그대로 들어간다: 같은 질문(태그 2개가 전부 달린 제품)을 관계형은 한 번의 질의로 정확히 답하고, 문서형은 후보를 넓게 읽어 와 브라우저에서 깎는다. 읽기 요금과 정확도를 어디서 치르느냐의 차이다.
