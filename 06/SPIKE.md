# S06 스파이크 기록

## 2. `/dp/` 원본 HTML에 리뷰가 있나 — **안 됐다** (2026-09-08)

**판정 질문:** 우리가 이미 받는 아마존 상품 페이지(`/dp/ASIN`) 원본 HTML에 리뷰 본문이
몇 개 들어 있나? 5개 이상이면 「보드에서 가져오기」를 붙이고, 아니면 붙여넣기만.

**방법:** `initial-b06` 서버리스에서 직접 fetch → `data-hook="review-body"` 정규식 카운트.
버릴 코드(`api/spike.js`, mode=reviews/find).

| 시도 | 결과 |
|---|---|
| 1~2회 (두 ASIN) | 4KB 봇 페이지 — 새 프로젝트 IP를 첫 요청부터 차단 (S04 패턴) |
| 재시도 40초 간격 | 2회차에 진짜 페이지 1253KB 수신, **리뷰 본문 0개** |
| `find` 모드로 마커 전수 조사 (1009KB 정상 페이지) | `review-body` 0 · `review-text-content` 0 · `customer_review-` 0 · `reviewsMedley` 0 · "Top reviews" 0 |

**결론: 정규식 문제가 아니라 데이터 부재다.** 아마존은 리뷰 섹션을 서버 렌더에서 빼고
뒤늦게 하이드레이션한다 — S03 Yelp에서 적은 "렌더된 화면과 서버가 받는 것은 다르다"의
세 번째 재현. 리뷰 전용 페이지(`/product-reviews/`)는 로그인 벽이라 기획서의
「안 만드는 것 1번」 그대로 손대지 않는다. **「보드에서 가져오기」는 안 만든다. 입력은
붙여넣기 하나.** 골이 붙여넣기라 완료 판정은 흔들리지 않는다. `BRD_WS`도 이번 주엔 불필요.

**셋업 시간:** 약 12분 (06/ 생성 → initial-b06 → 배포 → 첫 판정. 봇 페이지 대기 포함)

**막힌 지점 1개:** 새 Vercel 프로젝트의 첫 요청들이 전부 봇 페이지 — 판정 대상이 "정규식이
맞나"였는데 실제로는 "진짜 페이지를 받았나"부터 갈라야 했다. `bot` 관측값을 응답에 같이
찍어둔 덕에 두 질문이 섞이지 않았다.

**문서 품질:** 해당 없음 (HTML 파싱) **무료 한도:** 비용 0
