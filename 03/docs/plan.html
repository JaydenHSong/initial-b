01누가 쓰나

매달 회식 장소를 정해야 하는 우리 팀. 특히 "이번엔 어디 가요?"를 채팅방에 던지고 답을 취합하는 총무 역할 — 한 달에 한 번, 회식 전 주마다 겪는 일이다.

02지금은

채팅방에 후보를 묻는다. 링크 몇 개가 올라오고 이모지 반응이 애매하게 갈리다가 스레드가 가라앉고, 결국 당일에 목소리 큰 사람 의견으로 정해진다. 누가 어디에 손들었는지는 스레드를 거슬러 올라가며 다시 세어야 한다.

03없앨 동작 하나

채팅 스레드를 거슬러 올라가며 표를 세는 것. 후보와 표가 한 화면에 있고, 1위가 항상 계산돼 있다.

04핵심 기능 1개

로그인한 팀원이 가게 이름(+링크·지역)을 넣으면 후보 카드로 등록되고, 각자 1표를 던지거나 옮기면 현재 1위가 바로 보인다.

Google 로그인 → 가게 이름 + 링크(Yelp·Google)·지역 입력 → 후보 카드 등록 → 투표(다른 후보를 찍으면 표가 옮겨간다) → 1위 표시. 회식일 라벨은 로그인한 사람이 앱에서 직접 셋팅한다(라운드 관리 아님 — 라벨 하나 덮어쓰기). 쓰기 경로가 S02와 정반대다: S02는 브라우저 읽기전용 + 서버(Admin SDK) 쓰기였고, 이번 주는 로그인한 브라우저가 Firestore에 직접 쓰고 보안 규칙이 막는다. 서버 함수는 0개다.

범위를 당겼다가 화요일에 되물렸다. Yelp 자동 수집(S04 카드 당겨 쓰기)을 계획했으나 스파이크에서 DataDome 차단 + 프록시 불안정으로 실패, 기획서에 적어둔 후퇴 경로대로 수동 입력으로 확정했다(SPIKE.md). 이번 주 주제는 어디까지나 인증이다. 수집은 S04에 비동기 구조로 재도전.

05안 만드는 것 3개

  • 회식 라운드/이력 관리 — 후보 풀 하나만. 회식이 끝나면 투표는 콘솔에서 리셋한다
  • Yelp 검색·자동완성 — 링크 붙여넣기만. 검색을 붙이는 순간 범위가 터진다
  • 댓글·수정 UI — 잘못 올리면 본인이 지우고 다시 올린다 (본인 삭제만 허용 — 이건 이번 주 주제라 만든다)

06성공 판정

  • 두 계정으로 각자 Google 로그인이 된다 (입력 필드 0개)
  • 가게 이름을 넣으면 후보 카드가 등록된다 (링크·지역은 참고용으로 카드에 붙는다)
  • 각자 1표를 던지고, 다른 후보를 찍으면 표가 옮겨진다 — 어떤 방법으로도 1인 2표가 안 된다
  • 현재 1위가 화면에서 바로 보인다
  • 남의 후보 삭제 시도가 보안 규칙에서 거부되고, 본인 것은 지워진다
  • 새로고침·다른 기기에서 같은 보드가 보인다 (하드코딩 아님)
  • Firebase 웹 설정 외에 비밀 키가 브라우저에 노출되지 않는다 (서버 함수 0개)
  • 1인 1표를 스키마(투표 문서 ID = uid)로 어떻게 보장했는지 설명한다

07내 옵션 + 이유

Firebase Auth (Google 로그인). S02의 Firestore를 이어 쓰면 인증과 데이터 권한이 한 생태계에서 연결되는 것(보안 규칙의 request.auth)을 바로 볼 수 있다. 이번 주 주제가 "인증이 데이터 모델에 미치는 영향"인데, 문서형에는 unique 제약이 없어서 1인 1표를 문서 경로(votes/{uid})로 풀어야 한다 — 관계형이면 unique(user_id) 한 줄인 것을 경로 설계로 푸는 차이를 몸으로 확인한다(S05 Postgres 주에 반대쪽을 확인할 비교거리). Google 로그인이라 가입·비번 화면이 없고 입력 필드 0개로 제약도 통과한다.

08리스크 + 검증법

걱정되는 것: ① Yelp 크롤링 차단 — 아마존이 S02에서 3일 만에 차단한 전례가 있고 Yelp도 봇 차단이 심하다고 알려져 있다. ② 보안 규칙이 실제로 남의 글 삭제와 중복 투표를 막아주나.
화요일 스파이크로 확인: 1순위 — 서버리스에서 Yelp 가게 페이지의 이름·별점·인기 메뉴가 긁히나 (공식 Fusion API의 키·요금도 같이 확인). 안 긁히면 그날 안에 "이름만 수동 입력"으로 후퇴. 2순위 — Google 로그인 두 계정으로 남의 문서 삭제·votes/{남의uid} 쓰기를 시도해 규칙이 거부하는지 실호출로 확인.
