# S03 스파이크 기록

## 1. Yelp 수집 — **안 됐다 (직접 경로)** (2026-08-18)

**판정 질문:** Vercel 서버리스(데이터센터 IP)에서 Yelp 가게 페이지를 받아
이름·별점·가격대·인기 메뉴가 나오나?

**대상:** `https://www.yelp.com/biz/jinsol-gukbap-buena-park-buena-park`

### 먼저 확인한 것 — 데이터는 페이지 안에 있다 (2026-08-17, 브라우저)

기획 단계에서 내 브라우저로 먼저 봤다. 필요한 필드가 전부 있었다:

| 필드 | 값 | 어디에 |
|---|---|---|
| 이름 | Jinsol Gukbap Buena Park | `<title>` · `og:title` |
| 별점 · 리뷰 수 | 4.3 · 388 | `aria-label="4.3 star rating"` |
| 가격대 | $$ | 임베디드 JSON (`&quot;` 이스케이프) |
| 인기 메뉴 | 김치찜 · 돼지갈비 · 육개장 등 10개 | `/menu/<가게>/<메뉴>` 링크 |

**여기서 한 번 틀렸다.** 렌더된 DOM에는 JSON-LD(`@type: Restaurant`)가 있어서
"JSON-LD 하나로 끝나겠다"고 봤는데, **JS 없이 받은 원본 HTML에는 JSON-LD가 없다.**
JS가 나중에 심는 것이었다. 원본에서는 위 표의 경로로 따로 뽑아야 한다.
S02에서 "압축을 안 풀고 문자열을 찾으면 조용히 빈손"이던 것과 같은 종류의 착각이다 —
**렌더된 화면에서 본 것과 서버가 받는 것은 다르다.**

### 판정: 데이터센터 IP는 첫 요청부터 차단

| 시도 | status | bytes | 결과 |
|---|---|---|---|
| 기본 UA + accept (3회) | **403** | 779 | 차단 |
| 풀 브라우저 헤더 (sec-ch-ua, sec-fetch-*, upgrade-insecure-requests 등) | **403** | 776 | 차단 |

**차단 주체는 DataDome이다.** 응답 헤더 `server: DataDome`, 본문은 CAPTCHA 배달
스크립트(`geo.captcha-delivery.com/c.js`)와 "Please enable JS and disable any ad blocker".

**S02 아마존과 다른 점:** 아마존은 8/7에 4회 연속 성공하고 사흘 뒤 막혔다.
Yelp은 **첫 요청부터** 막힌다. 헤더 위조로는 안 뚫린다 — DataDome은 JS 챌린지와
IP 평판을 같이 보기 때문에 헤더만 손봐서는 통과할 수 없다.

**셋업 시간:** Vercel 프로젝트 생성 → 함수 배포 → 첫 판정까지 약 15분

**막힌 지점 1개 — 환경변수 복사가 성립하지 않는다.**
프록시 폴백(S02에서 쓴 Bright Data)을 붙이려고 `initial-b02`의 `BRD_WS`를
`initial-b03`으로 옮기려 했다. `vercel env pull`로 받아 파이프로 넘겼는데
연결이 `Invalid URL`로 죽었다. 값의 길이를 재보니 **11자 —
`[SENSITIVE]` 문자열 그 자체였다.**

**Vercel CLI는 암호화된 환경변수를 pull할 때 실제 값 대신 `[SENSITIVE]`
플레이스홀더를 쓴다.** 프로젝트 간 시크릿 복사는 CLI로 안 되고, 원본
(Bright Data 대시보드)에서 다시 가져와야 한다. 값이 없는 게 아니라
**있는 것처럼 보이는 가짜 값이 들어가서** 에러 메시지가 엉뚱한 곳
(`Invalid URL`)을 가리켰다 — S02에서 "에러 메시지에 판단을 미리 섞지 말고
관측값을 남겨야 한다"고 적었던 것과 같은 함정이다. 길이와 스킴만 재보니
1분 만에 갈렸다.

**문서 품질:** 해당 없음 (공식 API가 아니라 HTML 파싱)

**무료 한도:** 직접 fetch는 비용 0이나 통과율 0%.

### 프록시 재판정 (2026-08-18 오후, BRD_WS 원본 값 재등록 후)

Bright Data 스크래핑 브라우저로 4런을 돌렸다. **뚫리긴 하는데 흔들린다:**

| 런 | 시간 | 결과 |
|---|---|---|
| 1 | 38.3s | **성공** — 이름·별점 4.3·인기 메뉴 3개 (가격대는 null) |
| 2 | 22.2s | 전부 null — 하이드레이션 전에 파싱함 |
| 3 | 17.3s | 전부 null — 관측값: 1.19MB 껍데기 + 빈 `<title>` |
| 4 | 47.1s | 네비게이션 타임아웃 (45s 상한) |

**막힌 지점 1개 더 — 대기 조건이 이스케이프 페이로드에 속았다.**
Yelp 원본 HTML은 빈 껍데기 + 이스케이프된 JS 페이로드 1.19MB다. 하이드레이션을
기다리려고 `/star rating/` 문자열 매칭을 걸었는데, 이 문자열이 **이스케이프된
페이로드 안에 이미 있어서** 즉시 통과했다 — 렌더 완료가 아니라 페이로드 도착을
기다린 셈이다. 런 1의 성공은 프록시가 느려서 우연히 하이드레이션이 끝난 뒤였다.
DOM 노드(`[aria-label*="star rating"]`) 대기로 바꾸자 이번엔 goto 자체가
45초를 넘겨 죽었다 (런 4).

**내 추측:** DataDome 챌린지 해소 시간이 런마다 다르고, 1.2MB + JS 하이드레이션이
서버리스 함수 상한(60s) 안에 안정적으로 안 끝난다. 성공해도 등록 UX가 건당
17~47초다. S02 아마존(건당 ~11초)보다 한 단계 나쁘다.

### B안 시도 — 하이드레이션 우회 (2026-08-18 오후, 3수 두고 중단)

런 2·3이 1.19MB를 받고도 실패한 이유가 "파서가 하이드레이션된 DOM만 찾아서"였으므로,
**이스케이프된 페이로드를 정규화(`\"`·`&quot;` 풀기)해 정규식으로 직접 뽑는** 파서로
바꿨다. 대기 시간이 통째로 사라지는 수였는데:

| 수 | 결과 |
|---|---|
| 이스케이프 파서 (3런) | **1,555B 챌린지 페이지**가 domcontentloaded로 잡힘 — Bright Data가 챌린지를 푸는 건 그 뒤였다 |
| + 페이로드 대기 (>400KB) | 런1 네비게이션 타임아웃(40s), **런2 1.19MB 수신했으나 파싱 전부 null**, 런3 셸 2분 상한 초과 |

오늘 프록시 총 ~11런 중 4필드가 나온 건 1런. 소요 9~47초, 타임아웃 ~40%.
**결론: 뚫리는 날도 있지만 서버리스 60초 상한 + DataDome 변동성 조합으로는
"링크 넣으면 카드 등록"이라는 UX가 성립하지 않는다.** 파싱 null 원인(직렬화 시
이스케이프 형태 차이로 추정)을 더 팔 수는 있으나, 그 밑에 또 뭐가 있을지 모르는
우물이라 3번 규칙으로 끊었다.

**결정 (기획서 리스크 항목의 후퇴 경로 발동): 수동 입력으로 후퇴한다 (화요일 안 확정).**
후보 등록은 가게 이름 + Yelp 링크(참고용, 수집 안 함) 입력 필드 2개.
서버 함수는 0개가 됐고, 스파이크 코드(`api/yelp-proxy.js`)는 폐기했다.
수집 재도전은 S04(크롤링 주)에 "등록은 즉시, 수집은 백그라운드로 채우는"
비동기 구조로 — 40초 지연이 UX가 아니라 파이프라인이 되게.

### 덧붙임 (수요일 8/19) — 구글 지도는 열려 있었다

같은 질문을 Google Maps에 1회성 프로브(직접 fetch, 프록시 없음)로 던져봤다:

| 대상 | status | bytes | 관측 |
|---|---|---|---|
| maps/search | 200 | 203KB | 0.56초 · 동의벽/캡차 없음 · `APP_INITIALIZATION_STATE` 데이터 블롭 존재 |
| maps/place | 200 | 200KB | 0.48초 · 이름·별점 패턴 존재 |

**Yelp 403 vs Google 200 — 차단 정책은 사이트마다 완전히 갈린다.** 같은
데이터센터 IP인데 Yelp은 첫 요청부터 막고 구글은 그냥 준다. S02 교훈대로
"오늘 열려 있다"가 "계속 열려 있다"는 아니다(아마존은 사흘 만에 막혔다).

**이번 주에는 통합하지 않는다** — 수요일이고, 후퇴는 화요일에 확정했으며,
데이터 블롭 파싱(중첩 JS-JSON)은 그 자체로 반나절거리다. **S04 크롤링 주의
1순위 재료로 넘긴다:** 직접 fetch 0.5초면 비동기 큐도 필요 없을 수 있다.
프로브 코드는 판정 후 제거했다.

### 재확인 (금요일 8/20) — 구글도 "열림"과 "추출"은 다르다

데모 준비 중 "링크 넣으면 자동으로"를 Google로 다시 시도했다. place 프로브를
붙여 실측하니 — maps/search·maps/place·?q=·google 검색 모두 **200·0.6초, 차단
없음**이지만 **이름·별점·주소가 raw HTML에 없다.** 202KB 껍데기 안엔 protobuf
블롭만 있고(내가 뽑은 "주소"는 base64 덩어리였다), Yelp과 똑같이 필드가 별도
호출로 하이드레이션된다. 수요일 노트의 "구글은 열려 있다"는 **HTTP 접근이
열렸다는 뜻이지 추출이 쉽다는 뜻이 아니었다** — 그때 hasName/hasRating을 느슨한
불리언으로 봐서 착시가 있었다.

**결론 재확인: 후퇴가 맞았다.** 자동 추출을 하려면 (a) protobuf 블롭 파싱(우물)
또는 (b) 공식 Places API(키+과금)뿐이다. 데모 아침이라 3수 규칙으로 끊고,
**정식 API 경로를 S04 재료로** 남긴다(직접 스크래핑이 아니라). 프로브는 제거했다.

## 2. Firebase Auth + 보안 규칙 — **됐다** (2026-08-18)

**판정 질문:** Google 로그인이 붙고, 남의 문서 삭제와 `votes/{남의uid}` 쓰기가
보안 규칙에서 실제로 거부되나?

**방법:** `firestore.rules`에 S03 규칙 추가(콘솔 게시) + 버릴 판정 페이지
(`spike-auth.html`, 판정 후 폐기). 비로그인 절반은 REST로, 로그인 절반은
실계정 2개로 갈랐다.

| 판정 | 결과 |
|---|---|
| Google 제공자·승인 도메인 | 활성 (authUri 발급으로 확인) |
| 비로그인: 읽기 / candidates·votes 쓰기 | 200 / **PERMISSION_DENIED ×2** |
| 계정 A: 내 후보 등록 · 내 투표 · 표 옮기기(같은 문서 덮어쓰기) | 허용 |
| 계정 A: 위조 등록(ownerUid=남) · votes/{남의uid} 쓰기 | **거부** |
| 계정 B: **남의 후보 삭제 시도** | **규칙이 거부 (PASS)** — 이번 주 데모 멘트의 근거 |
| 계정 B: 내 후보 삭제 | 허용 — 저장소에서 교차 확인 (B 후보 소멸 · A 후보 잔존) |
| S02 products 규칙 | 안 깨짐 (읽기 200 유지) |

**셋업 시간:** 약 45분 (규칙+판정 페이지 작성·배포 15분, 콘솔 설정 3가지와
로그인 경로 이슈 포함 판정 30분)

**막힌 지점 1개:** **임베디드 브라우저에서는 Google 로그인이 안 된다.**
앱 안의 미리보기 패널에서 로그인 시도가 조용히 실패했다 — Google이
임베디드 웹뷰의 OAuth를 정책으로 차단한다(`disallowed_useragent`).
일반 크롬에서는 즉시 성공. 데모도 반드시 일반 브라우저에서 한다.

**문서 품질:** 상 — 콘솔 3단계(제공자 켜기·도메인 추가·규칙 게시)로 끝났고,
규칙 문법(`request.auth`·`request.resource.data`)은 에러 메시지가 친절하다.

**무료 한도(Spark):** 소셜 로그인은 무료(과금은 SMS 전화 인증뿐). 이번 주 비용 0.

**미확인 1개:** 계정 B의 `votes/{B-uid}` 문서가 리스트에 없었다 — B에서
2번(자동 판정)의 투표 줄이 실행됐는지 로그로 확인 못 했다. 규칙 자체는
A 계정 + 비로그인 REST로 이미 갈렸으므로 판정에는 영향 없음.

**정리 필요:** 스파이크가 심은 `candidates` 1건(spike-hoon.iccorp)과
`votes` 1건은 수요일 구현 전에 콘솔에서 지운다 — 데모 데이터는 실제
등록 흐름으로 넣는다(S02 원칙 그대로).
