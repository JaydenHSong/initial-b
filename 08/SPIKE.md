# S08 스파이크 기록 (2026-09-24 목, 하루 압축 스프린트)

## 1. Supabase Realtime — 두 탭에 전달되나, 지연은 몇 ms인가 — **됐다**

**판정 질문:** 정적 페이지가 `postgres_changes`를 구독하면 다른 탭의 변경이 오나? 지연은?

**방법:** `s08_stock`을 `supabase_realtime` 발행에 추가 + `replica identity full`. 브라우저는
supabase-js(CDN)로 UPDATE 이벤트를 구독. 지연은 **보낸 탭이 클릭 시각(epoch ms)을 행에 실어
(`sent_at`) 받는 탭이 도착 시각과 뺀다** — 같은 기기라 시계가 같다. DB의 `updated_at`은
서버 시계라 브라우저와 어긋나서 못 쓴다.

| 방향 | 표본 (ms) | RPC 왕복 |
|---|---|---|
| A(판다) → B(수달) | 547 · 606 · 312 · 552 | 291ms |
| B → A | 291 | 115ms |

**중앙값 ~550ms, 최소 291ms.** 지연의 절반 이상이 쓰기(RPC) 왕복이고 발행→도착은 ~250ms.
두 탭의 수량이 매번 일치했다. 폴링(S04·S05, 3~4초 주기)이었다면 평균 1.5~2초·최대 3~4초 +
매 주기 읽기 비용 — 이번 주 데모 멘트의 근거.

**셋업 시간:** 약 10분 (테이블+발행 마이그레이션 → v0 화면 배포 → 첫 이벤트 수신)

**막힌 지점 1개:** "지연을 무엇으로 재나"가 설계 문제였다 — `updated_at`(서버 시계)로 재면
시계 오차가 섞인다. 클라이언트 시각을 함수 인자(`p_sent_at`)로 실어 행에 남기는 것으로 정리.
함수 시그니처를 바꾸느라 이전 오버로드를 drop해야 했다(안 지우면 PostgREST가 모호성 에러).

**문서 품질:** 상 — 발행 추가 한 줄 + `.channel().on('postgres_changes')` 구독으로 첫 시도에 됐다.
**무료 한도:** Realtime 동시 연결 200 · 메시지 200만/월 (Free) — 팀 규모 무관.

## 2. 쓰기 경로 — anon은 RPC로만, 직접 UPDATE는 막히나 — **됐다**

| 판정 | 결과 |
|---|---|
| anon `PATCH /s08_stock` (qty=999) | HTTP 200이지만 **행 변화 없음** — RLS에 쓰기 정책이 없어 조용히 걸러진다 |
| anon `rpc/adjust_stock(+1)` | 17 → 18 |
| 동시 +1 ×5 (병렬 curl) | 18 → **23** — `qty = qty + delta`가 직렬화돼 충돌 없음 |
| −100 | **0**에서 멈춤 (`greatest(0, …)`) |

함수는 `security definer`로 테이블을 만지고, anon엔 그 함수 실행 권한만 준다. 브라우저에
시크릿이 없고 서버 함수도 없다 — 이번 주는 브라우저↔DB 직결.

**정리 필요:** 없음 — 스파이크 화면이 곧 제품 화면이다(버릴 코드가 없었다).
