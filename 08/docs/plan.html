01누가 쓰나

같은 재고 보드를 동시에 보는 스피겐 창고·CS 담당자들. 한 사람이 출고를 찍는 동안 다른 사람은 그 수량을 보고 고객에게 답한다.

02지금은

공유 시트를 열어두고 새로고침. 몇 초 전 값을 보고 답하거나, 두 사람이 같은 칸을 동시에 고쳐 한쪽이 덮어쓴다.

03없앨 동작 하나

"바뀌었나?" 하고 새로고침하는 것 — 서버가 먼저 알려준다.

04핵심 기능 1개

재고 보드에서 SKU 수량을 −/+로 바꾸면 같은 보드를 연 다른 탭이 수백 ms 안에 바뀐다. 각 탭은 마지막으로 받은 변경의 지연 시간(ms)을 찍는다 — 보낸 탭의 클릭 시각과 도착 시각의 차. 증감은 DB 함수 안에서 원자적이라 동시 클릭이 충돌하지 않는다.

05안 만드는 것 3개

  • 품목 추가·삭제·이름 편집 — SKU 5개를 SQL로 시드. 보드는 수량만 바꾼다
  • 재고 이력·감사 로그 — 행에 updated_at·updated_by 두 칸까지. 누가 언제 얼마나 바꿨는지 목록은 없다
  • 로그인·사용자별 보드 — 공용 보드 1개. 탭 식별은 랜덤 별명(같은 기기 두 탭 구분용). 폴링 토글·재연결 UI·낙관적 UI도 없음

06성공 판정

  • 탭 두 개 나란히 → 한쪽 + → 다른 쪽 수량이 바뀌고 지연 ms가 찍힌다 (실측 291~606ms)
  • 두 탭이 동시에 +를 눌러도 수량이 정확히 합산된다 (병렬 5회 → +5)
  • 브라우저에 시크릿 없음 — anon 키 + DB 함수 하나. 직접 UPDATE는 RLS가 막는다

07내 옵션 + 이유

넷 중 폴링은 S04·S05에서 이미 써봤고(3~4초 주기), 이번 주는 "서버가 먼저 알려주는" 쪽을 만져야 카드가 새 것이다. Supabase Realtime은 지금 쓰는 DB 테이블의 변경을 WebSocket으로 밀어주니 발행 한 줄로 켜지고 서버 함수가 0개다 — Firestore 리스너는 더 성숙하지만 데이터가 Supabase 궤도 밖으로 나간다. 쓰기는 DB 함수(RPC) 하나로만 열어 홉을 최소로 하고(지연 측정값이 좋아진다) 증감을 원자적으로 만들었다 — 브리프의 "충돌"에 대한 답.

08리스크 + 검증법

걱정되는 것: ① postgres_changes가 정적 페이지에서 붙고 두 탭에 오나 ② 지연을 무엇으로 재나(서버 시계 vs 브라우저 시계) ③ anon 키로 쓰기를 어디까지 열어야 하나
스파이크로 확인 (목 오전): ① 두 탭 양방향 5표본 291~606ms, 중앙값 ~550 ② 보낸 탭의 클릭 시각을 행(sent_at)에 실어 같은 기기에서 뺀다 ③ 직접 UPDATE는 RLS가 조용히 거르고 RPC만 통과, 병렬 +1×5가 정확히 +5. 상세 08/SPIKE.md. 후퇴 경로(3초 폴링)는 쓸 일 없었다.
